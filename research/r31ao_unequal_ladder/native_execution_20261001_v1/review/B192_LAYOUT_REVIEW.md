# Independent bounded B192 layout decision

**Admit the historical x87 layout for the two exact recovered B192 archives and their hash-bound extended NPY members.** This is permission to interpret those represented bytes exactly under the reviewed evidence chain; it is not a continuum-error certificate or production/scientific admission.

| Archive | Reviewed SHA256 |
|---|---|
| `OD_ASSEMBLED_OD.npz` | `7e7b5782cc698a364aeac608620e56c7bfdc64035ffe5dfee501608dae7970df` |
| `independent_JVP_ASSEMBLED.npz` | `53569e92875254e897a7e23b55620cca9c5acf9f86124dc0a73198ad41d1df87` |

The admitted extended layout is little-endian x87-80, 16 bytes per component, ten meaningful bytes at offset zero, and real component before imaginary component for 32-byte complex elements. Preserve all raw bytes and padding as provenance; six component-padding bytes do not contribute to the numerical value. Apply each NPY member's own C/Fortran order. The integer `n.npy` is metadata and outside this extended floating-point decision.

The independent probe freshly rehashed both NPZs and all 13 NPY members/payloads, verified six producer source files against both historical pre/post locks, and checked that the OD and JVP output identities separately match their prepared native identities. OD is not admitted merely by borrowing JVP's native binary identity. It has its own pinned driver, native identity, source aliases and common serializer chain.

The historical environment records NumPy 2.3.5, x86_64 Linux, 16-byte long doubles with 64 significant bits and 32-byte complex long doubles. The pinned JVP adapter calls the pinned C++ probe and rejects a mismatch between C `sizeof`, `LDBL_MANT_DIG`, complex size and those actual NumPy properties. This runtime check's successful execution is inferred from the recorded successful source-bound producer transaction; no new native probe was run and no missing original probe-output array is invented.

The source-bound JVP scalar `z=3/4` has the exact x87 encoding at offset zero, and not binary128's encoding. The pinned NumPy implementation uses native long-double components in real/imaginary order and writes numeric array bytes without a precision conversion. In addition, the reviewer independently checked the actual OD bytes against its pinned statement `O_row=O.conj().T`: **all 94 pairs** have identical first-component meaningful bytes and exactly the x87 sign-bit flip in the second component (byte 25 of the 32-byte element). Matching the C-order `(47,2)` original to the Fortran-order `(2,47)` transpose preserves physical element position. This is direct file evidence for component order and sign position, not a numerical plausibility argument.

The decision relies on the preserved historical producer/source/version records as execution provenance. It does not claim recovery or byte attestation of the historical NumPy extension binary, arbitrary distributions carrying the same version label, a current-host dtype test as historical evidence, or a cryptographically complete operating-system custody chain. Requiring the original wheel was a stronger evidence route introduced in a previous audit, not the only way to establish this bounded layout. The new source and byte witnesses close the concrete representation ambiguity for these exact files without changing the target or weakening numeric error requirements.
